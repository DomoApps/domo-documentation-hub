THE BACKLOG MODEL
-----------------

Every ticket in the Asana backlog lives as a record in:
    scripts/backlog_manifest.json

That file is the single source of truth for where each ticket stands.
Each record has:

  task_id          — Asana global ID
  name             — ticket title
  bucket           — A (skip/meta) | B (update self-contained) |
                     C (update needs attachment) | D (net-new self-contained) |
                     E (net-new with attachment) | F (article missing) |
                     M (unparseable notes)
  asana_url        — link to the ticket
  description      — parsed body from the submission form
  articles[]       — referenced article IDs + resolved repo paths (EN/JA)
  attachments[]    — list with attachment_id, name, host, local_path under .asana-cache/
  execution        — null | {status: applied|needs_manual_review, edits: [...]}
  done_check       — null | {git_status, content_check, ...} (from earlier audit)
  disposition      — null | "completed: ..." | "won't do: ..." | etc.

A ticket is DONE when either:
  - execution.status == "applied"  AND  the Asana ticket is closed, OR
  - disposition starts with "completed:" or "won't do:" (and Asana closed)

The Asana ticket needs to be closed via API in both cases. There is no
"close in Asana" field — track that by re-querying Asana, or by trusting
that anything in scripts/reports/asana_close_results.json was closed.

CONVENTIONS / GOTCHAS THIS SESSION TAUGHT US

* "Cloud Amplifier" → "Cloud Integrations" rebrand. Default to plural.
  Use singular "Cloud Integration" only with a determiner (a/an/the/this/
  each/new). In JA, keep the English "Cloud Integrations" label by
  default; some JA articles use クラウド統合 for the running-text
  instance form. Image alt text, URL paths, and anchor IDs with
  "cloud-amplifier" are preserved.

* UI labels in **[...]** brackets. Conservatively preserve until the
  in-product UI label is confirmed renamed. Once Jared confirms the
  product has shipped a UI rename, flip them. See commit ae243cef
  (flip of 4 UI labels) for the pattern.

* GitHub secret scanning. The Service Token JSON example in
  s/article/360042932334.mdx originally contained
  "MIIEvQIBADANBgkqh..." which is the standard PKCS#8 prefix for any
  RSA-2048 private key. The scanner pattern-matched on it even though
  it was placeholder. Commit a0b3bde4 replaced it with unambiguous
  <angle-bracket> placeholders. If you write similar examples, avoid
  PEM BEGIN/END markers and don't include any string that resembles
  the start of a real cryptographic value.

* Okta procedure rewrite (commit c9efe77b) was authored from the
  model's training-data knowledge, not from the live UI. Don't repeat
  that pattern. If a ticket says "the UI has changed" and offers a
  test instance or a Zoom, take the offer (or hand back to the user).

* Sub-agent context. Each sub-agent burns ~20–60k tokens. The
  parity sweep cost ~1M tokens across 48 sub-agents. Budget
  accordingly; batch sub-agent dispatches when independent and
  serialize when they target the same file.
