## Intro

This article explains how to configure scheduled data freshness checks and data caching for a Cloud Integration, including how to set a default cache duration and override it for individual DataSets.

---

## Overview

Cloud Integrations DataSets stay current through two mechanisms that you configure per integration:

- **Data freshness checks —** Domo polls your source cloud warehouse on a schedule to detect when the underlying data has changed. When an update is detected, connected cards, alerts, and DataFlows reflect the new data on their next load. Domo also performs on-demand freshness checks when a query is executed and the configured cache duration (TTL) has expired, providing more responsive data without relying solely on scheduled polling.
- **Data caching —** Domo stores the results of card queries temporarily. When a user opens a card, Domo returns the cached result if one exists rather than sending a new query to the warehouse. This reduces query load on your warehouse. You can set a default cache duration for the integration and override it for individual DataSets.

Data freshness checks are configured at the integration level and apply to all DataSets in that integration. Data caching uses a default cache duration set at the integration level, which you can override for individual DataSets.

## Open the Integration Settings

To configure data freshness and caching for an existing integration:

1. Navigate to **Data Warehouse** > **Connect Data** > **Manage existing integrations**.

2. Select the tile for your integration type, such as Snowflake or BigQuery.

3. Find the integration you want to configure, select the wrench icon <i className="icon-wrench sm" aria-hidden="true" />, and then select **Integration settings**.

   <Frame><img src="/images/kb/dataset-level-caching-01.png" alt="Integration list with the wrench menu open" /></Frame>

4. Scroll to the **Data Freshness** and **Data Caching** cards, or select them in the left menu.

   <Frame><img src="/images/kb/dataset-level-caching-03.png" alt="Integration Settings page showing the Data Freshness and Data Caching cards" /></Frame>

## Configure Data Freshness Checks

1. On the **Data Freshness** card, select **Edit**.

2. Enable the **Schedule data freshness checks** toggle.

3. Select the **Basic** or **Advanced** tab to set when Domo checks for updates.

### Basic

Basic mode lets you choose a preset update interval from a dropdown. Set the **Start Time** and **Time Zone** to control when within the interval checks begin. For sub-daily intervals (every 15 minutes, every 30 minutes, every hour), you can also enable **Active hours** to restrict checks to a defined time window.

<Frame><img src="/images/kb/data-freshness-04.png" alt="Basic tab with the update interval dropdown open" /></Frame>

| Update interval  | Description                                                             |
| ---------------- | ----------------------------------------------------------------------- |
| Every 15 minutes | Checks every 15 minutes, all day or during the configured active hours. |
| Every 30 minutes | Checks every 30 minutes, all day or during the configured active hours. |
| Every hour       | Checks every hour, all day or during the configured active hours.       |
| Every day        | Checks once per day at the specified time, including weekends.          |
| Every weekday    | Checks once per day at the specified time, excluding weekends.          |
| Every week       | Checks once per week on the selected day at the specified time.         |
| Every month      | Checks once per month on the selected date at the specified time.       |

### Advanced

Advanced mode gives you granular control over check frequency, day of the week, and monthly schedule. Configure all three settings to define exactly when checks run.

<Frame><img src="/images/kb/data-freshness-06.png" alt="Advanced tab with Once a day selected" /></Frame>

**How frequently?**—How often within a day checks run:

- **Once a day —** Checks run once per day at the time and time zone you specify.
- **More than once a day —** Checks repeat throughout the day at the interval you specify. Enable **Active hours** to restrict checks to a defined window, such as 8 AM–6 PM.

<Frame><img src="/images/kb/data-freshness-07.png" alt="Advanced tab with More than once a day selected and Active hours enabled" /></Frame>

**Day frequency**—Which days checks run:

- **Every day —** Checks run every day of the week.
- **Specific days of the week —** Checks run only on the days you select.
- **Specific days of the month —** Checks run only on the calendar dates you select.

**Month frequency**—Which months checks run:

- **Every month —** Checks run every month.
- **Specific months —** Checks run only in the months you select.

## Configure Data Caching

Caching uses a default cache duration set for the integration. You can override the default for individual DataSets.

### Set the Default Cache Duration

The default cache duration applies to every DataSet in the integration that doesn't have its own cache duration.

1. On the **Data Caching** card, select **Edit**.

   You can also go to **Dataset Settings** and select **Edit default**.

2. Make sure the **Enable caching** toggle is on.

3. Select a **Cache duration (TTL)**. The maximum is 1 day.

   <Frame><img src="/images/kb/dataset-level-caching-05.png" alt="Data Caching dialog with the Cache duration (TTL) dropdown open" /></Frame>

4. Select **Save**.

If you change the default later, every DataSet without an override uses the new value.

### Set the Cache Duration for a DataSet

1. In the integration's left menu, select **Dataset Settings**.

   <Frame><img src="/images/kb/dataset-level-caching-06.png" alt="Dataset Settings page with the default cache duration and the DataSets table" /></Frame>

2. Find the DataSet. You can use **Search**, **Add filter**, or **Sort by**.

3. In the **Caching** column, select a duration from the DataSet's dropdown. To always query the warehouse for this DataSet, select **No caching**.

   <Frame><img src="/images/kb/dataset-level-caching-08.png" alt="Caching dropdown for a DataSet showing Revert to default and No caching" /></Frame>

To remove an override, select **Revert to default** in the dropdown.

### Set the Cache Duration for Multiple DataSets

1. On the **Dataset Settings** page, select the checkbox for each DataSet.

   <Frame><img src="/images/kb/dataset-level-caching-10.png" alt="Two DataSets selected with the Edit cache duration button" /></Frame>

2. Select **Edit cache duration**.

3. Select **Override default caching schedule**, and then select a **Cache duration (TTL)**.

   To remove the overrides and use the default instead, select **Reset to default caching schedule**.

   <Frame><img src="/images/kb/dataset-level-caching-13.png" alt="Cache duration dialog for two DataSets with 2 hours selected" /></Frame>

4. Select **Apply**.

<Note>**Note:** The **Dataset Settings** page doesn't mark which DataSets have their own cache duration. A DataSet has an override when its **Caching** value differs from the **Default cache duration**.</Note>

## FAQ

### Data Freshness

<AccordionGroup>

<Accordion title="Why doesn't my data appear to be up to date?">
Make sure data freshness is enabled and configured to an interval that suits your use case. If data freshness is disabled, card query results may be cached for up to 24 hours.
</Accordion>

<Accordion title="Does data freshness work when my integration uses OAuth authentication?">
No. Data freshness checks and caching depend on the service account used to connect your integration. These features are disabled when using OAuth.
</Accordion>

<Accordion title="Can I manually refresh a Cloud Integration's data?">
Yes. In addition to scheduled freshness checks, a Cloud Integration provides an on-demand refresh you can trigger manually rather than waiting for the next scheduled check.

<Accordion title="Why doesn't my Cloud Integration DataSet show run history, an accurate last-run time, or a row count?">
Cloud Integration DataSets are queried live from your cloud warehouse rather than ingested into Domo on a schedule, so they don't produce the run-by-run execution history that scheduled connector or Magic ETL DataSets do. Instead of reporting a last-run time from an ingestion job, Domo reflects data currency through the scheduled freshness checks described above: when a check detects that the source data has changed, connected cards, alerts, and DataFlows pick up the new data on their next load.

Row counts and last-updated timestamps are available for table-backed DataSets but not for DataSets backed by a database View, because external warehouses don't expose those values for Views the way they do for tables. For more detail, see [Cloud Integrations Overview](/s/article/4412849158167).

### Caching

<AccordionGroup>

<Accordion title="When does Domo always query the warehouse instead of using the cache?">
Domo bypasses the cache and always sends a fresh query in these situations:

- Viewing the DataSet preview on the DataSet's Details page
- Loading a DataSet View
- Loading a DataSet into Magic ETL
- **Dynamic SQL functions**: Queries that include functions such as NOW(), CURRENT_DATE(), or CURRENT_TIMESTAMP() generate a unique SQL string on each execution. Caching is keyed on the exact SQL query, so these queries do not reuse cached results regardless of TTL setting.
</Accordion>

<Accordion title="Is the warehouse queried every time you view a card?">
No. When you view a card, Domo first checks for a cached result. If one exists, Domo returns the cached data. If none exists, Domo queries the warehouse.
</Accordion>

<Accordion title="Is the warehouse queried when someone edits a card?">
Yes. When building or editing a card in Analyzer, each change triggers a new query if **Auto Preview** is enabled.
</Accordion>

<Accordion title="Does opening a page with many cards query the warehouse once per card?">
Yes. Each card issues its own query, so opening a page—including an Overview page—that contains many cards built on a Cloud Integration can send one query per card to your cloud warehouse on first load. Caching mitigates this: once a card's result is cached, reopening the page returns the cached result instead of re-querying the warehouse until the Cache Duration (TTL) expires. To reduce warehouse load, enable caching and set a TTL that suits your freshness needs, and limit the number of live-source cards on frequently viewed pages.

{/* [pm-input] Jordan Jensen — Confirm whether a dedicated control to pause or cap per-card queries against a live Cloud Amplifier source (beyond caching/TTL) exists or is a tracked feature request. Synthesized from community forum reports; needs confirmation. */}
</Accordion>

<Accordion title="How long are card query results cached?">
Domo caches card query results until the cache duration (TTL) expires. The cache duration is set by the integration's default or by a DataSet's own cache duration, and the maximum is 1 day.
</Accordion>

<Accordion title="Is there a limit on the number of queries Domo will cache?">
No. There is no explicit limit on the number of cached query results.
</Accordion>

<Accordion title="Is there a data size limit on what Domo will cache?">
No. There is no row or data size limit on what is saved in the card cache.
</Accordion>

<Accordion title="Can I set a different cache duration for individual DataSets?">
Yes. Set a default cache duration for the integration, then override it for individual DataSets on the **Dataset Settings** page. For more information, see [Set the Cache Duration for a DataSet](#set-the-cache-duration-for-a-dataset).
</Accordion>

<Accordion title="What happens to DataSets with their own cache duration when I change the default?">
They keep their own cache duration. Only DataSets without an override use the new default.
</Accordion>

</AccordionGroup>
